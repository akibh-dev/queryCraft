# Integration and release checklist

The coordinator owns the release decision. Keep this checklist in the release PR and record the tested commit, model version, browser, build command and outcome. A failed critical journey goes back to its ticket owner with reproduction steps.

## Test the game that players receive

Use a clean install and the production build. Start each fresh-player test with an empty browser profile. Use the production service worker only in offline/update cases so a stale worker cannot mask a failed build.

## Offline, deployment and recovery

1. Generate a cache list from the actual Vite build output, including HTML, bundles, dynamic imports, bundled levels, fonts/icons and manifest assets. Use same-origin, build-versioned caches. A service worker installs only after its required files cache successfully. Cache navigation fallback HTML for known game routes; missing asset URLs must never receive HTML as a successful script response.
2. Keep an existing tab on a coherent build when a new version is available. Offer reload after the player finishes the current attempt. Delete only obsolete QueryCraft caches once safe. Keep progress in versioned localStorage. The manifest supplies app name, theme color, start URL, display mode and legible 192/512 icons.
3. Visit the deployed preview online, wait for service worker readiness, then go offline and reload a challenge URL. Open a level never visited in that profile, change an index, Run, Submit and reload. Repeat online with a newer build and verify the upgrade retains progress. Document first-visit offline limitations.
4. Configure an assets-only Cloudflare Workers deployment pointing at dist with SPA navigation fallback. Serve immutable caching for hashed assets and revalidation for HTML and the service worker. Configure headers for same-origin assets and script execution, frame protection, content-type sniffing and referrer policy. Verify headers and route fallback on the hosted preview. Use the current supported Cloudflare CLI for a new project; pin the tested tool and record the exact deploy command at implementation. [Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/) · [Cloudflare CLI](https://developers.cloudflare.com/cf/agents/)
5. Deploy a preview when deployment is in scope. Smoke-test home, a refreshed deep link, mobile controls and an offline level on that hostname. Publish the verified artifact on the selected hostname of the owner's active Cloudflare zone. Check HTTPS, deep links and a real solve on the final hostname. Browser storage is origin-specific; test preview and production independently. [Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/)
6. Record source tag, deployment ID, model version and previous known-good deployment. For a failed release, restore the previous deployment; test an existing browser profile as well as a fresh one. Confirm the service worker update and compatible save recovery. Keep an export available before a migration that changes the save format.

## Reviewable launch materials

- README with working setup, checks, screenshots, learning goals, local data behavior and playable URL.
- Model guide with units, constants, rounding rules, version changes and supported SQL subset. Authoring guide with one level, its reference attempt and validation command.
- Architecture and accessibility notes, contributor guide, security reporting information, changelog, project license approved by the owner, and attribution for any bundled assets.
- Issue templates, release notes and a short gameplay capture from the verified build. External announcements are separate publication actions.

The critical path to launch is one independently validated solution for every level, a usable keyboard/mobile journey, local recovery and offline checks on the hosted build. Mark any manual check that has only been planned as pending until someone performs it.
